# GitHub Actions workflows

The repository uses GitHub Actions for continuous integration, validation against GTFS datasets,
packaging, publishing, release tasks, and deployment of the web application.

This page provides an overview of the workflows in `.github/workflows/`. For implementation details,
the workflow YAML files remain the source of truth.

## Continuous integration and validation

| Workflow | File | Purpose |
| --- | --- | --- |
| Test Package Document | [`test_pack_doc.yml`](../.github/workflows/test_pack_doc.yml) | Runs the main test matrix, packages the CLI snapshot JAR, and builds Javadoc. It runs for changes targeting `master` and for releases. |
| Rule acceptance tests | [`acceptance_test.yml`](../.github/workflows/acceptance_test.yml) | For applicable pull requests targeting `master`, builds the pull-request and `master` validator JARs, runs them against GTFS datasets from the Mobility Database, compares their reports, and posts the acceptance-test result on the pull request. See [Acceptance tests](ACCEPTANCE_TESTS.md). |
| End to end | [`end_to_end.yml`](../.github/workflows/end_to_end.yml) | Runs the validator against GTFS datasets and collects validation reports as workflow artifacts. See [Reproducing errors](REPRODUCE_ERRORS.md). |
| Format code | [`formatting.yml`](../.github/workflows/formatting.yml) | Checks Java formatting for pull requests and reports files that do not satisfy the formatter. |
| Docker image | [`docker.yml`](../.github/workflows/docker.yml) | Runs the Java tests, builds and tests Docker images for `linux/amd64` and `linux/arm64`, and pushes the resulting multi-platform image for `master` pushes and releases. |
| Web client CI | [`web_client_pr.yml`](../.github/workflows/web_client_pr.yml) | Runs web-client checks when a pull request changes `web/client`. |
| Web client Cypress e2e tests | [`web_client_test.yml`](../.github/workflows/web_client_test.yml) | Runs Cypress end-to-end tests for web-client pull-request changes and preserves screenshots or videos as artifacts when applicable. |
| Web service CI | [`web_svc_pr.yml`](../.github/workflows/web_svc_pr.yml) | Runs web-service checks when a pull request changes `web/service`. |

## Packaging and publishing

| Workflow | File | Purpose |
| --- | --- | --- |
| Package Installers | [`package_installers.yml`](../.github/workflows/package_installers.yml) | Builds CLI and GUI artifacts and platform-specific installers. |
| Upload Release Assets | [`publish_assets.yml`](../.github/workflows/publish_assets.yml) | For release runs, generates and uploads the CLI JAR, GUI JAR, `rules.json`, and zipped Javadocs as release assets; the workflow also runs the Maven Central publishing task. |
| Publish Jars Snapshots | [`publish_snapshots.yml`](../.github/workflows/publish_snapshots.yml) | Publishes snapshot JARs when relevant core modules or build configuration change on `master`, and can also be run manually. |
| Update NOTICE_MIGRATION.md | [`notice_migration_generation.yml`](../.github/workflows/notice_migration_generation.yml) | Manually generates notice-migration information by comparing rule data for the previous and specified releases, then creates a pull request containing the documentation update. See the [release instructions](RELEASE.md). |

For instructions on downloading a CLI snapshot artifact produced by GitHub Actions, see
[Downloading the latest snapshot JAR](DOWNLOAD_SNAPSHOT_JAR.md).

## Common workflow considerations

Some workflows deliberately ignore documentation-only or unrelated file changes. A workflow not
starting for a particular pull request therefore does not necessarily indicate a failure.

Artifacts generated by GitHub Actions are downloaded as archives. Where a workflow uploads a JAR,
extract the downloaded artifact before running the JAR. See
[Downloading the latest snapshot JAR](DOWNLOAD_SNAPSHOT_JAR.md).

When reproducing a validation problem against a particular GTFS feed, use the
[reproducing errors guide](REPRODUCE_ERRORS.md) rather than modifying the general workflow
configuration without a specific reason.

For release-specific workflow steps, follow [the release guide](RELEASE.md).
